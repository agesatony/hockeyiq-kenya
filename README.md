# HockeyIQ Kenya

🔗 [View the live dashboard](https://agesatony.github.io/hockeyiq-kenya/)

HockeyIQ Kenya turns Kenya Hockey Union's raw match results into a real, working intelligence report — league tables, team and player analytics, Elo-based ratings, and Kenya's international hockey record — rebuilt automatically every week straight from KHU's own published results. No manual spreadsheets, no stale numbers: every table and chart updates itself as new matches are played.

This README is the operational guide for how the pipeline works. For a full findings/limitations audit, see **[AUDIT.md](AUDIT.md)** — read that before treating anything here as "verified working," since several claims below could not be tested end-to-end in the environment that assembled this repo.

## Project structure

```
notebooks/
  01_scraping.ipynb            Domestic scrape: 8 competitions, matches, events, player stats
  02_league_analytics.ipynb    League tables, scorer/discipline/form analytics
  03_advanced_analytics.ipynb  44-module advanced analytics + the dashboard builder (Module 35)
  04_international.ipynb       Kenya national-team record (FIH TMS), rankings, ACCC medals
  05_worldcup_live.ipynb       Fast, standalone FIH World Cup 2026 standings refresh
data/
  raw/                         Scraper output, one row per match/event/player-stat
  processed/                   Analytics output consumed by the dashboard
reports/
  dashboard.html               Generated by 03 — this is the actual site
scripts/
  post_to_linkedin.py          Builds and posts a real-data digest to LinkedIn
.github/workflows/
  domestic-weekly.yml          01->02->03->04, weekly, deploys to Pages, posts weekly digest
  worldcup-live.yml            05 + dashboard rebuild, every 3h during the WC window, deploys to Pages
  worldcup-daily-digest.yml    One LinkedIn post/day during the WC window (decoupled from the above)
requirements.txt
AUDIT.md                       Full findings, what's fixed, what's unverified, go-live checklist
```

All notebooks use paths like `../data/processed/...`, so they must be run
**from inside `notebooks/`** (the workflows already do this via
`working-directory: notebooks`).

## How it stays up to date

1. **`domestic-weekly.yml`** runs every Monday: scrapes all 8 domestic
   competitions plus Kenya's international record, rebuilds every
   analytics module and the dashboard, commits the refreshed CSVs and
   `dashboard.html` back to the repo, deploys the dashboard to GitHub
   Pages, and posts a league-leaders digest to LinkedIn.
2. **`worldcup-live.yml`** runs every 3 hours during 15–30 August only:
   re-scrapes just the single fast World Cup standings page, then
   re-runs the dashboard notebook (cheap — it's pure pandas over already-
   saved CSVs, no re-scraping of the slow domestic pipeline) so the
   published site picks up fresh pool standings same-day.
3. **`worldcup-daily-digest.yml`** posts one World Cup context update to
   LinkedIn per day during the tournament — deliberately separate from
   the 3-hourly data refresh above, so LinkedIn gets a daily digest, not
   a post every 3 hours.

Both data workflows also support **manual runs**: Actions tab → pick the
workflow → "Run workflow". Do this once before relying on the schedule —
see the go-live checklist below.

## One-time setup (required before anything runs for real)

1. **Push this repo to GitHub** with this exact structure.
2. **Enable Pages**: repo Settings → Pages → Source = "GitHub Actions".
   (You do not need to create a `gh-pages` branch or a `docs/` folder —
   the workflows upload the dashboard as a Pages artifact directly.)
3. **Run `domestic-weekly.yml` manually once** (Actions tab → "Run
   workflow") and check the run logs. This is the first real execution
   of the Selenium scrapers against the live sites from a GitHub-hosted
   runner — confirm it completes and inspect the committed
   `data/raw/*.csv` for sane output before trusting the schedule.
4. **(Optional) Set up LinkedIn posting** — see below. The pipeline runs
   fine without this; the LinkedIn step just logs a message and exits
   cleanly (`continue-on-error: true`) if the secrets aren't set.

## LinkedIn setup (optional — the site works without it)

LinkedIn posting requires your own LinkedIn Developer App and an OAuth
access token — this is not something that can be set up on your behalf
without your LinkedIn login, so these steps are for you to complete:

1. Create an app at [linkedin.com/developers](https://www.linkedin.com/developers/apps).
2. Request the **"Share on LinkedIn"** product (for posting as yourself)
   or the **Community Management API** product (for posting to a Company
   Page you administer). LinkedIn reviews/approves these — this can take
   time and isn't instant.
3. Complete the OAuth 2.0 flow to obtain an access token with
   `w_member_social` scope (personal profile) or `w_organization_social`
   scope (Company Page). LinkedIn's own [OAuth quickstart docs](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2)
   walk through this; it requires a one-time browser-based consent step
   you do yourself.
4. Get the **author URN**:
   - Personal profile: `urn:li:person:{id}` — obtained from the
     `/v2/userinfo` (OpenID) or `/v2/me` endpoint using your own token.
   - Company Page: `urn:li:organization:{id}` — the numeric ID is visible
     in your Page's admin URL.
5. In your GitHub repo: Settings → Secrets and variables → Actions → New
   repository secret. Add `LINKEDIN_ACCESS_TOKEN` and `LINKEDIN_AUTHOR_URN`.
6. **Operational note:** LinkedIn's standard member access tokens expire
   (commonly 60 days) and this project does not implement a refresh-token
   flow. Budget for reissuing the token periodically, or extend
   `scripts/post_to_linkedin.py` to use LinkedIn's refresh-token flow if
   you want this fully hands-off. This is stated plainly rather than
   promised as "fully automatic forever" — see AUDIT.md.

Test locally before relying on the scheduled workflow:
```
python scripts/post_to_linkedin.py --dry-run          # prints the post, calls no API
LINKEDIN_ACCESS_TOKEN=... LINKEDIN_AUTHOR_URN=... python scripts/post_to_linkedin.py --strict
```

## Known, documented data limitations (surfaced on the dashboard itself)

- Player-level stats (Top Scorers, Player Influence Index, Squad
  Reliance, Coach/Scout Intelligence) are built from goal-by-goal event
  detail present in roughly a fifth of matches with a recorded goal —
  this is a confirmed gap in KHU's own source data, not a scraping
  shortfall, and the dashboard states the exact coverage percentage on
  its front page and above the affected tables.
- Penalty corner/stroke goal-type tagging does not exist anywhere in the
  domestic source data (confirmed, not assumed) — only the international
  (FIH TMS) data source has this breakdown.
- International coverage spans 6 confirmed competitions, 2017–2025 — not
  a complete history; FIH's own system only reliably covers 2013 onward.
- The FIH per-match statistics PDFs (possession, shots, circle entries)
  were confirmed to return all-zero values across every match tested —
  this data source is real but not currently usable.
